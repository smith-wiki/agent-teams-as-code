# Sleeping is a runtime concern, not an agent role

A useful split is **agent definition → account reconciler → session coordinator → sandbox runtime**. The definition says *who* may act and *with which capabilities*; the reconciler provisions external identities; the coordinator accepts messages, owns the durable conversation and work product, and chooses when to run; the runtime supplies an isolated process. This split is a proposed architecture, not a feature of AX ([AX Task and Workspace concepts](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md), [AX Task API](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/pkg/apis/v1alpha1/ax.proto)).

For a rarely active agent, a safe lifecycle is: reconcile its accounts and bindings; record inbound events in a durable queue/session store; on an event, acquire that agent/session's exclusive lease, restore relevant history and artifacts, run the agent, commit outputs and an event cursor, then release execution capacity. The external event source stays available while the execution process sleeps. Define what happens to in-flight tool calls before suspension and deduplicate event delivery on restart; a filesystem checkpoint alone cannot make an external side effect atomic.

**AX as one possible execution backend:** its `Task` specifies image, command, environment and workspace bindings; the API exposes `SuspendTask` and `ResumeTask` ([schema and RPCs](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/pkg/apis/v1alpha1/ax.proto)). In the documented runner, suspension preserves `/workspace`, while resume starts a **new process**, not suspended RAM. Persist the session and tool-event cursor yourself, then explicitly rehydrate the agent ([runner contract](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md)). AX `Ready` only reports sandbox/workspace readiness; the command's exit status is not currently reported to the control plane. The coordinator needs its own outcome and artifact protocol ([runner contract](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md)). AX does not model a team, agent identity, or conversation session ([AX concepts](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/concepts.md), [API schema](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/pkg/apis/v1alpha1/ax.proto)). Automatic idle suspension is on its [roadmap](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/roadmap.md), not something to assume today.

Current Agent Substrate distinguishes `Full` snapshots (including process memory) from `Data` snapshots (durable directories only); this does **not** make AX's `/workspace`-only resume memory-preserving ([Substrate glossary](https://github.com/agent-substrate/substrate/blob/22ba860e0f32e20713165b96abd81f6f96da620c/docs/glossary.md), [AX runner](https://github.com/google/ax/blob/e09ed1bc5463ad4b5ca88f755a6e1e2005b3c7b7/docs/runner.md)). Start with a simple wake-on-event coordinator and cold starts; add AX/Substrate only when measured idle capacity and isolation needs justify that stack.
