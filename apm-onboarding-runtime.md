# Takeaway: APM bootstraps and launches; it does not operate agent identities

**APM is useful on the packaging/launch side of the boundary.** `scripts:` maps names to shell commands; `apm run [name]` compiles referenced prompt files, substitutes declared parameters, and executes the command in the current shell. It is a foreground launcher, not a durable agent service ([`apm run`](https://microsoft.github.io/apm/reference/cli/run/)). Microsoft’s official GitHub Action installs the CLI, runs `apm install`, and can optionally compile and invoke one manifest script through its `script` input; CI scheduling, credentials and runner lifetime still come from GitHub Actions ([`microsoft/apm-action`](https://github.com/microsoft/apm-action)).

APM can install local runtime CLIs and remove only runtimes it installed (`apm runtime setup/remove`). That “runtime” means a Copilot, Codex, Gemini or `llm` executable, not an agent process or account ([runtime reference](https://microsoft.github.io/apm/reference/cli/runtime/)). Likewise, `apm uninstall` removes package files and owned MCP/LSP configuration, not an agent identity ([uninstall reference](https://microsoft.github.io/apm/reference/cli/uninstall/)). MCP dependencies are materialized into selected harness configuration; OAuth-shaped fields are merely passthrough configuration for a pre-registered client. Required variables may be collected or rendered into native secret references, but APM does not perform the provider grant ([MCP install guide](https://microsoft.github.io/apm/consumer/install-mcp-servers/)). Policy can allow or deny packages, MCP servers and transports, while manifest-script policy is audit-only; `apm run` re-enforces no policy and token/OAuth scopes are explicitly outside governance ([governance boundary](https://microsoft.github.io/apm/enterprise/governance-guide/#4-what-you-cannot-govern)).

The current published manifest and root CLI registration expose no first-class per-agent account, provider grant, durable session, sleep/wake or provider-event subscription resource ([manifest schema](https://microsoft.github.io/apm/reference/manifest-schema/), [CLI registration source](https://github.com/microsoft/apm/blob/main/src/apm_cli/cli.py)). APM lifecycle events are hooks around install/update/uninstall, not external event listeners. Trusted project hooks can call a user-supplied provisioning command or HTTPS webhook, but project-source hooks are skipped by default until explicitly trusted; that command/service must implement onboarding itself ([lifecycle reference](https://microsoft.github.io/apm/reference/cli/lifecycle/)).

The smallest credible addition is a thin reconciler plus worker and tiny durable mapping store **if unattended operation is needed**: derive agents from repository files; call each provider’s existing admin/API, or record a manual onboarding result where no API exists; persist agent-to-provider IDs and grant state; receive provider webhooks/polls; launch or resume work; checkpoint session state; and revoke grants on removal while deactivation/deletion follows an explicit retention policy. Keep APM for install/audit/config projection and optional one-shot launch. If agents are invoked only by a human in an already configured harness, manual provider onboarding may be enough; build only the missing automation.
