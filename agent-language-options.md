# Choose the deployer first, then write its agent resource

**Revised recommendation for k3s + Kata:** choose the deployer and its Pod runtime constraint before a profile format. [SIG Apps Agent Sandbox v1.0.4](microsandbox-kubernetes.md#k3s-and-kata-a-real-pod-sandbox-not-an-agent-definition) accepts `spec.podTemplate.spec.runtimeClassName` and reconciles a Kata-backed Pod, but reads only an OCI workload description: the image must contain an executable agent and its harness must receive the role, model and tools. [kagent 0.10.2](agent-control-plane-options.md#k3s-and-kata-neither-semantic-agent-cr-can-select-the-runtime) interprets declarative prompt/model/tools in an `Agent` CR yet does not expose runtime-class selection for its generated Deployment. `.agent.md` is optional client-facing content, not a controller contract; Nix may build a chosen agent image but cannot make an arbitrary profile executable without a harness.

These languages describe different seams. The table records documented behavior, not a reason to pick a speculative agent-file standard before selecting its controller.

## Actual deployer inputs

| Target | Authored source | Interpretation |
|---|---|---|
| [kagent 0.10.x](agent-control-plane-options.md#kagent-release-split-and-authoring-contract) | `kagent.dev/v1alpha2 Agent` YAML | `Declarative` contains agent behavior; `BYO` supplies an A2A-serving image, so behavior stays inside that image. `kagent.yaml` is an optional CLI project file converted to the CRD. **Neither Agent mode exposes `runtimeClassName`** at v0.10.2; a separate Pod-admission policy or node default would be needed for Kata ([verified deployment gap](agent-control-plane-options.md#k3s-and-kata-neither-semantic-agent-cr-can-select-the-runtime)). |
| [SIG Apps Agent Sandbox v1.0.4](microsandbox-kubernetes.md#k3s-and-kata-a-real-pod-sandbox-not-an-agent-definition) | `agents.x-k8s.io/v1beta1 Sandbox` YAML | `spec.podTemplate.spec.runtimeClassName` selects the installed Kata class; the controller reconciles the image's Pod and storage. The agent's instructions, tools and model client remain native to the harness in the image or its mounted configuration. This is not superradcompany Microsandbox. |
| [Microsandbox](microsandbox-kubernetes.md) | CLI `sandbox.yaml` with `msb run --conf`, or SDK arguments | Creates a local guest; changing the file is not reconciliation. Do not claim that a future Kubernetes operator will consume this file. |

## From an agent description to a Kata-backed process

Separate three inputs: (1) the authored role/instructions/tools in whatever format the chosen **harness** consumes; (2) an image with that harness, startup behavior and model access, built from those sources or configured through mounted data; (3) a `Sandbox` resource referring to the image and the already configured Kata `RuntimeClass`. Neither a profile file nor a bare `Sandbox` resource creates a functioning agent alone ([Sandbox scope](https://github.com/kubernetes-sigs/agent-sandbox/blob/v1.0.4/README.md), [Kubernetes runtime selection](https://kubernetes.io/docs/concepts/containers/runtime-class/)). If the agent *description itself* must be the watched Kubernetes resource, kagent Declarative is closer, but Kata then requires a separately owned Pod mutation or node-wide runtime default ([comparison](agent-control-plane-options.md#k3s-and-kata-neither-semantic-agent-cr-can-select-the-runtime)). Do not select a conversion format for the user's existing descriptions before seeing their shape and intended harness.

Neither supplies agent semantics, image construction, reconciliation, or provider APIs by itself. |
| Reproducible files and runtime image | **Nix/NixOS** | The [Nix language](https://nix.dev/manual/nix/stable/language/) composes derivations, and Nixpkgs builds [OCI container artifacts](https://nixos.org/manual/nixpkgs/stable/#sec-pkgs-ociTools). | Build a pinned agent image for the selected controller. Nix is the build language, not the controller's desired-state schema. |
| Kubernetes-specific agent API | **kagent 0.x `Agent`; separate 1.x alpha API** | The shipped [0.x `kagent.dev/v1alpha2 Agent`](https://kagent.dev/docs/kagent/0.x/concepts/agents/) reconciles declarative agents or A2A-compatible BYO images to Deployments. ## Which existing language is the safest reuse bet?

The evidence below separates **documented consumption** from ecosystem likelihood. Any statement about what an unspecified future controller is likely to import is necessarily **inference**, not a market-share measurement or a vendor commitment.

| Candidate | Direct adoption or implementation evidence | Maturity, portability, and operational gap |
|---|---|---|
| **AGENTS.md** | OpenAI Codex documents its discovery and override order for [`AGENTS.md`](https://learn.chatgpt.com/docs/agent-configuration/agents-md), and GitHub Copilot documents nearest-file precedence for the same format in [coding-agent repositories](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions). OpenAI donated the format to the Linux Foundation's Agentic AI Foundation and names several products that had adopted it at donation time ([announcement](https://openai.com/index/agentic-ai-foundation/)). | The format is deliberately [ordinary Markdown with no required fields](https://agents.md/), so there is no versioned persona, tool, model or runtime contract to validate. Its neutral stewardship and separately documented consumers are strong direct evidence for **repository-wide instructions**, not for a named or deployable agent. |
| **Agent Skills `SKILL.md`** | Claude Code says it follows the [Agent Skills open standard](https://code.claude.com/docs/en/skills); OpenAI documents the same package format for [ChatGPT and Codex](https://learn.chatgpt.com/docs/build-skills); and GitHub documents skill discovery across its [cloud agent, code review, CLI, app and VS Code agent mode](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills). | The [current specification](https://agentskills.io/specification) defines a directory with required `SKILL.md` metadata/body and optional scripts, references and assets, but marks `allowed-tools` experimental. Its own [contribution policy](https://github.com/agentskills/agentskills/blob/main/CONTRIBUTING.md) calls the project early-stage and says the core specification is still being iterated. This is the strongest direct cross-vendor evidence for a reusable **capability package**, not a persistent persona, member, runtime or deployment. |
| **GitHub Copilot / VS Code custom-agent Markdown** | GitHub documents repository profiles under `.github/agents/` and their use by the [Copilot coding agent and supported IDE/CLI surfaces](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-custom-agents); VS Code documents reusable [`.agent.md` role configurations](https://code.visualstudio.com/docs/copilot/customization/custom-agents). The [configuration reference](https://docs.github.com/en/copilot/reference/custom-agents-configuration) defines a Markdown instruction body plus fields such as `description`, `name`, `tools`, `model`, invocation controls and MCP servers, and pins a running task to a Git commit. | This is the best documented, already implemented **named persona/profile** among the candidates. It is nevertheless a GitHub/Microsoft-family contract, and the reference explicitly records fields that are IDE-only, unavailable in IDEs, or ignored on some surfaces. Even the apparent APM bridge is not a common tools contract: APM authors `tools` as a [mapping and says Copilot deployment is verbatim](https://microsoft.github.io/apm/producer/author-primitives/instructions-and-agents/#agents), while GitHub requires `tools` to be a [list or string](https://docs.github.com/en/copilot/reference/custom-agents-configuration). GitHub also says omitting `tools` enables every available tool and unrecognized names are ignored, so the portable profile is **not a permission boundary**. Only display name, description and instruction content are a defensible portable subset; model and tool policy require target adapters plus independent enforcement. It does not specify an image, process, secrets, durable state or reconciliation. |
| **Microsoft APM `.apm/agents`** | Microsoft's CLI contains a maintained [target matrix](https://microsoft.github.io/apm/reference/targets-matrix/) that maps APM primitives into Copilot, Claude, Codex, Cursor, Gemini, OpenCode and other native trees. | Those converters are direct evidence that the **APM implementation** emits those targets, not evidence that their vendors natively consume `.apm`. Both OpenAPM [v0.1](https://microsoft.github.io/apm/specs/openapm-v01/#status-of-this-document) and the CLI's manifest [v0.3](https://microsoft.github.io/apm/reference/manifest-schema/#status-of-this-document) are editor's working drafts; the former explicitly disclaims backward compatibility before 1.0. Runtime APIs are out of scope, so build, execution and reconciliation remain external. |
| **Oracle Open Agent Spec** | Oracle ships real exporter/loader implementations for WayFlow, OpenAI Agents, Microsoft Agent Framework, LangGraph and AutoGen in the [26.3.1 cross-framework guide](https://oracle.github.io/agent-spec/26.3.1/howtoguides/howto_execute_agentspec_across_frameworks.html). | This is stronger than a schema-only proposal, but the documented adapters are all supplied by the Oracle project rather than independent vendor-owned consumers, and loading requires the caller to provide a tool registry. Its versioned release is credible implementation evidence, not proof that the interchange preserves every framework behavior or supplies deployment, secrets, state and reconciliation. |
| **Snap Agent Format** | Snap publishes a versioned [1.0 JSON Schema](https://agentformat.org/schema/1.0/agentformat-schema.json). Its launch article says Snap uses internal adapters for Google ADK, LangChain and PydanticAI plus its internal Auton SDK and Console ([first-party description](https://eng.snap.com/agent-format)). | The same article says only the specification is public and presents it as a proposed community answer. The claimed adapters and runtime are therefore not independently inspectable public integrations; a `1.0` schema label alone does not establish ecosystem adoption or operational portability. |
| **A2A Agent Card / OASF record** | A2A is a Linux Foundation protocol with a released [1.0.0 specification](https://a2a-protocol.org/v1.0.0/specification/) and official [Python, Go, Java, JavaScript, .NET and Rust SDKs](https://a2a-protocol.org/latest/sdk/). OASF publishes a versioned [agent-record schema and validator](https://docs.agntcy.org/oasf/agent-record-guide/), and its SDK implements a concrete [`RecordToA2A` conversion](https://github.com/agntcy/oasf-sdk/blob/main/USAGE.md). | This is the strongest governance/versioning and implementation story in the set, but at a different seam: A2A standardizes communication with an already running opaque agent, while OASF standardizes catalog/discovery metadata. Neither authors the persona or provisions the runtime described by its record/card. |

**Earlier, profile-first comparison (now conditional):** GitHub/VS Code custom-agent Markdown (`.github/agents/<profile>.agent.md`) is useful when *reusing a named instruction profile among those clients* is a separate requirement. Keep portable profile content to `name`, `description` and Markdown instructions; `model`, `tools` and permissions are not interchangeable across clients ([GitHub reference](https://docs.github.com/en/copilot/reference/custom-agents-configuration)). This is **not** a deployer API: neither kagent’s `Agent` nor Agent Sandbox’s `Sandbox` documents direct consumption of `.agent.md`. A committed opaque `metadata.agentId` can annotate a GitHub profile when needed for identity, but [IDE clients do not use that metadata](https://docs.github.com/en/copilot/reference/custom-agents-configuration); do not impose the profile or its ID scheme before selecting the controller.

At the adjacent seams, retain `AGENTS.md` for repository policy and `SKILL.md` packages for reusable capabilities. Their independently documented consumers make them safer cross-vendor bets for those jobs, but promoting either to “the agent language” would erase the distinction between context, capability and persona. A2A/OASF should be generated for deployed discovery; richer APM, Oracle and Snap descriptors remain optional adapters until independent consumers and compatibility guarantees exist. None of these formats replaces the image, secret binding, mutable provider state or reconciliation boundary below.

Two newer profile contenders also do not choose a deployer. Open Agent Format [says most platforms have not fully integrated it](https://openagentformat.com/) and offers mappings. GitAgent has a [git-native runtime](https://github.com/open-gitagent/gitagent), but that proves its own implementation, not that the Kubernetes or Microsandbox controllers above consume its repository layout.

APM and Nix operate at the build/materialization seam. APM projects authored primitives and locked packages into [harness-native trees](https://microsoft.github.io/apm/reference/targets-matrix/); Nix can package such a tree or build one directly into the agent image. Neither tool changes the installed controller’s input schema. Use APM only when its adapters or dependencies justify it; otherwise let the selected harness’s native configuration live in the image, with a `kagent Agent` or `Sandbox` resource governing its deployment. Normal [sandboxed Nix builds](https://nix.dev/manual/nix/stable/command-ref/conf-file.html#conf-sandbox) need explicit dependency inputs rather than relying on network access.

**Separate concern, not a controller-selection gate:** an image can carry runtime binaries, instructions and non-secret defaults, but does not establish mutable provider accounts. If such accounts are needed later, their [identity reconciliation](identity-reconciliation.md) and secret references remain outside the image. This does not disqualify a controller that successfully deploys the agent.

**Composition after selecting a deployer:** on Kubernetes, use the chosen controller’s committed `Agent` or `Sandbox` resource files as the deployment membership source; do not hand-maintain a second list of the same agents. Build any BYO image with Nix and put its agent-specific configuration in the harness format that image actually reads. `.agent.md` can be an optional client profile, not an obligatory compiler input. With mandatory Microsandbox and no released controller, its create-time CLI/SDK contract is the only current runtime input; a reconciled desired-state language must wait for, or be implemented with, an actual lifecycle owner ([Microsandbox boundary](microsandbox-kubernetes.md)).
