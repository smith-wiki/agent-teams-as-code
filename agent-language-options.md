# Agent language: use an APM package plus sparse operator bindings

There is no demonstrated universal agent language. The candidates cover different seams:

- **Microsoft APM is the closest deployable repository contract.** An [APM package](https://microsoft.github.io/apm/concepts/package-anatomy/) contains `apm.yml` plus `.apm/agents/` and `.apm/skills/`; the files, not a separate team object, form the collection. Agent Markdown carries the role, model hint and tool list. The current [target matrix](https://microsoft.github.io/apm/reference/targets-matrix/) deploys agents to Copilot, Claude, Grok Build, Cursor, Codex, OpenCode and Kiro, but not Gemini or Windsurf, and transformations lose fields on some targets. Skills are package primitives, not a portable per-agent skill-binding model. Both [OpenAPM v0.1](https://microsoft.github.io/apm/specs/openapm-v01/#status-of-this-document) and the implemented [v0.3 manifest](https://microsoft.github.io/apm/reference/manifest-schema/#status-of-this-document) are working drafts.
- **Agent Format 1.0 is a promising IDL, not proven portability.** Its [JSON Schema](https://agentformat.org/schema/1.0/agentformat-schema.json) describes one agent’s identity, I/O, tools/MCP, constraints, local or remote sub-agents and execution policy. That can express orchestration, not an unordered repository collection. Snap explicitly says its Auton SDK, console and framework adapters are internal and [only the specification is public](https://eng.snap.com/agent-format); the public [repository](https://github.com/agent-format/agent-format-schema) currently supplies the schema, not those runtimes.
- **Oracle Open Agent Spec is more implemented but models execution.** It defines reusable Agents and Flows plus explicit `Swarm` and `ManagerWorkers` topology ([26.3.1 language spec](https://oracle.github.io/agent-spec/26.3.1/agentspec/language_spec_26_3_1.html)). Oracle ships PyAgentSpec, WayFlow and current adapters for OpenAI Agents, Microsoft Agent Framework, LangGraph and AutoGen ([adapter guide](https://oracle.github.io/agent-spec/26.3.1/howtoguides/howto_execute_agentspec_across_frameworks.html)). Making its topology authoritative would duplicate this repository’s intentionally independent membership.
- **A2A and OASF are complementary outputs.** An [A2A Agent Card](https://a2a-protocol.org/v1.0.0/specification/#44-agent-discovery-objects) describes an already served endpoint, skills and authentication requirements; an [OASF record](https://docs.agntcy.org/oasf/agent-record-guide/) is catalog/discovery metadata. Neither defines local role instructions, deployment or account creation.

An APM `.agent.md` is a **callable persona**, not an independent process specification ([authoring](https://microsoft.github.io/apm/producer/author-primitives/instructions-and-agents/#agents)). For one concrete deployment target, APM projects the file to `.opencode/agents/<name>.md` and OpenCode exposes `opencode run --agent <name>`; that selects a profile for a launched process, but other targets need their own invocation and may lose tool restrictions ([APM OpenCode target](https://microsoft.github.io/apm/reference/targets-matrix/#opencode), [OpenCode CLI](https://opencode.ai/docs/cli/#run-1), [APM agent transforms](https://microsoft.github.io/apm/producer/author-primitives/instructions-and-agents/#what-compiles-where-1)).

**Recommendation:** use APM as layer one now, with repository revision plus `.apm/agents/*` as membership and `apm.yml` for package metadata/dependencies. Add a **proposed sparse operational overlay**, keyed only by a stable agent ID, for exceptions such as runtime image/sandbox, model-secret reference and Slack/Zulip/mail identity. The operator discovers membership from APM and joins matching overrides; it must not maintain a second complete agent list. This overlay is deployment configuration, not a claimed extension to APM or a portable language guarantee.
