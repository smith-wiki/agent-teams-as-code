# Agent language: reuse a named profile, let Nix build the runtime

**Recommendation:** when future reuse matters, keep the agent's descriptive profile in the documented GitHub/VS Code custom-agent Markdown shape and let Nix project that content into the pinned harness's native files and container image. APM remains optional: adopt it only when its package graph or maintained target adapters are worth making APM the authoring source. If reuse stops being a requirement and every agent runs one harness, direct native-file generation is the simpler optimization.

There is still no demonstrated universal agent language. The useful choices describe different seams. The first three columns below summarize documented product behavior; “Use here” is the proposed architectural choice.

| Primary seam | Candidate | Documented behavior | Use here |
| --- | --- | --- | --- |
| Role/persona and harness materialization | **Microsoft APM** | An [APM package](https://microsoft.github.io/apm/concepts/package-anatomy/) has `apm.yml` and authored primitives under `.apm/`; install/compile produces target-native files. The [target matrix](https://microsoft.github.io/apm/reference/targets-matrix/) shows that primitive support and transformations differ by harness. An [agent primitive](https://microsoft.github.io/apm/producer/author-primitives/instructions-and-agents/#agents) is a named persona (model, instructions, tools), not an independently supervised process. | Best when one source must target several supported harnesses or consume APM packages. It is an alternative authoring source, not a necessary layer beneath the recommended `.agent.md` profile; use direct native generation only when cross-harness reuse is not a priority. |
| Live agent or workflow semantics | **Agent Format 1.0** | Its public [JSON Schema](https://agentformat.org/schema/1.0/agentformat-schema.json) describes identity, interface, tools/sub-agents, constraints and execution policy. Snap says the Auton SDK, console and framework adapters are internal; [only the specification is public](https://eng.snap.com/agent-format). | A possible execution IDL, not evidence of a portable runtime, repository membership model, image build, or provider onboarding mechanism. |
| Live agent or workflow semantics | **Oracle Open Agent Spec** | The [language specification](https://oracle.github.io/agent-spec/26.3.1/agentspec/language_spec_26_3_1.html) defines serializable Agents, Flows and orchestration components such as `Swarm` and `ManagerWorkers`. Oracle documents adapters for WayFlow, OpenAI Agents, Microsoft Agent Framework, LangGraph and AutoGen in its [adapter guide](https://oracle.github.io/agent-spec/26.3.1/howtoguides/howto_execute_agentspec_across_frameworks.html). | Useful if those execution graphs are the product. Making a topology authoritative would conflict with this design's independent agents and duplicate repository membership. |
| Repository data contract | **Plain YAML/JSON plus JSON Schema and generators** | [JSON Schema](https://json-schema.org/overview/what-is-jsonschema) defines and validates JSON structure and constraints; generation and operational meaning come from code written by this project. | Lowest-dependency option for sparse operational bindings keyed by stable agent ID. It is deliberately local, not a newly claimed agent standard; every output adapter remains ours to maintain. |
| Typed or templated configuration | **CUE / Jsonnet** | [CUE](https://cuelang.org/docs/introduction/) combines data, constraints, validation and code generation. [Jsonnet](https://jsonnet.org/learning/tutorial.html) is a hermetic JSON-generating language with imports, functions, composition and assertions. | Adopt only when validation/composition or template scale justifies another language and toolchain. Neither supplies agent semantics, image construction, reconciliation, or provider APIs by itself. |
| Reproducible files and runtime image | **Nix/NixOS** | The [Nix language](https://nix.dev/manual/nix/stable/language/) composes derivations—precise descriptions of how inputs derive files. Nixpkgs provides [`writeTextFile`](https://nixos.org/manual/nixpkgs/stable/#trivial-builder-writeTextFile), [`dockerTools.buildImage` / `buildLayeredImage`](https://nixos.org/manual/nixpkgs/stable/#sec-pkgs-dockerTools), and [`ociTools.buildContainer`](https://nixos.org/manual/nixpkgs/stable/#sec-pkgs-ociTools) for generated files and container artifacts; NixOS itself uses a [declarative system configuration](https://nixos.org/manual/nixos/stable/#sec-configuration-syntax). | Project the canonical profile into harness-native files, package the exact harness and dependencies, and publish one immutable image per descriptor revision. Nix is the build language, not the agent-profile schema. |
| Kubernetes-specific agent API | **kagent 1.x `Harness` + `AgentTemplate`** | The [1.x alpha model](https://kagent.dev/docs/kagent/1.x/about/core-concepts/) separates runtime/image/WorkerPool policy from model/prompt/tools and reconciles their combination on Agent Substrate; `AgentInstance` conversations live in its gRPC API/PostgreSQL, not in Git or a CRD. The distinct 0.x `AgentHarness` only provisions OpenClaw/Hermes and is [removed in 1.x](https://kagent.dev/docs/kagent/1.x/reference/release-notes/1.0/#removed-and-replaced-resources). | A more integrated language **if** we choose Kubernetes plus kagent's gVisor runtime. It cannot directly replace Microsandbox, does not provision external provider accounts, and a Nix-built BYO image must satisfy [kagent's A2A gRPC contract](https://kagent.dev/docs/kagent/1.x/agents/bring-your-own-agent/). See the [operator comparison](agent-control-plane-options.md#kagent-if-the-runtime-can-change). |
| Cluster desired state | **Kubernetes CRD plus controller** | A [custom resource](https://kubernetes.io/docs/concepts/extend-kubernetes/api-extension/custom-resources/) stores structured data; paired with a custom controller it becomes a declarative API whose controller drives current state toward desired state. | Good Kubernetes-facing API if Kubernetes is actually the control plane. It should not become the canonical agent language merely to support an optional deployment, because bare-metal operation would then inherit cluster concepts and machinery. |
| External infrastructure or accounts | **Terraform / OpenTofu / Pulumi** | Terraform and OpenTofu configurations declare provider-managed [infrastructure resources](https://developer.hashicorp.com/terraform/language) ([OpenTofu wording](https://opentofu.org/docs/language/)); Pulumi programs declare resource desired state and its engine computes operations to reach it ([Pulumi concepts](https://www.pulumi.com/docs/iac/concepts/)). | Appropriate for durable provider resources only where a provider exposes the needed API. Provider/state lifecycle is useful for shared infrastructure but is heavier than the agent descriptor and does not replace persona or image build. |
| Served-agent discovery | **A2A / OASF** | An [A2A Agent Card](https://a2a-protocol.org/v1.0.0/specification/#44-agent-discovery-objects) advertises a served endpoint, skills and authentication requirements; an [OASF record](https://docs.agntcy.org/oasf/agent-record-guide/) is catalog/discovery metadata. | Derive these after deployment if needed. Neither is repository membership, local instructions, image build, or account creation. |

## Which existing language is the safest reuse bet?

The evidence below separates **documented consumption** from ecosystem likelihood. Any statement about what an unspecified future controller is likely to import is necessarily **inference**, not a market-share measurement or a vendor commitment.

| Candidate | Direct adoption or implementation evidence | Maturity, portability, and operational gap |
|---|---|---|
| **AGENTS.md** | OpenAI Codex documents its discovery and override order for [`AGENTS.md`](https://learn.chatgpt.com/docs/agent-configuration/agents-md), and GitHub Copilot documents nearest-file precedence for the same format in [coding-agent repositories](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/add-custom-instructions/add-repository-instructions). OpenAI donated the format to the Linux Foundation's Agentic AI Foundation and names several products that had adopted it at donation time ([announcement](https://openai.com/index/agentic-ai-foundation/)). | The format is deliberately [ordinary Markdown with no required fields](https://agents.md/), so there is no versioned persona, tool, model or runtime contract to validate. Its neutral stewardship and separately documented consumers are strong direct evidence for **repository-wide instructions**, not for a named or deployable agent. |
| **Agent Skills `SKILL.md`** | Claude Code says it follows the [Agent Skills open standard](https://code.claude.com/docs/en/skills); OpenAI documents the same package format for [ChatGPT and Codex](https://learn.chatgpt.com/docs/build-skills); and GitHub documents skill discovery across its [cloud agent, code review, CLI, app and VS Code agent mode](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/add-skills). | The [current specification](https://agentskills.io/specification) defines a directory with required `SKILL.md` metadata/body and optional scripts, references and assets, but marks `allowed-tools` experimental. Its own [contribution policy](https://github.com/agentskills/agentskills/blob/main/CONTRIBUTING.md) calls the project early-stage and says the core specification is still being iterated. This is the strongest direct cross-vendor evidence for a reusable **capability package**, not a persistent persona, member, runtime or deployment. |
| **GitHub Copilot / VS Code custom-agent Markdown** | GitHub documents repository profiles under `.github/agents/` and their use by the [Copilot coding agent and supported IDE/CLI surfaces](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-custom-agents); VS Code documents reusable [`.agent.md` role configurations](https://code.visualstudio.com/docs/copilot/customization/custom-agents). The [configuration reference](https://docs.github.com/en/copilot/reference/custom-agents-configuration) defines a Markdown instruction body plus fields such as `description`, `name`, `tools`, `model`, invocation controls and MCP servers, and pins a running task to a Git commit. | This is the best documented, already implemented **named persona/profile** among the candidates. It is nevertheless a GitHub/Microsoft-family contract, and the reference explicitly records fields that are IDE-only, unavailable in IDEs, or ignored on some surfaces. Even the apparent APM bridge is not a common tools contract: APM authors `tools` as a [mapping and says Copilot deployment is verbatim](https://microsoft.github.io/apm/producer/author-primitives/instructions-and-agents/#agents), while GitHub requires `tools` to be a [list or string](https://docs.github.com/en/copilot/reference/custom-agents-configuration). GitHub also says omitting `tools` enables every available tool and unrecognized names are ignored, so the portable profile is **not a permission boundary**. Only display name, description and instruction content are a defensible portable subset; model and tool policy require target adapters plus independent enforcement. It does not specify an image, process, secrets, durable state or reconciliation. |
| **Microsoft APM `.apm/agents`** | Microsoft's CLI contains a maintained [target matrix](https://microsoft.github.io/apm/reference/targets-matrix/) that maps APM primitives into Copilot, Claude, Codex, Cursor, Gemini, OpenCode and other native trees. | Those converters are direct evidence that the **APM implementation** emits those targets, not evidence that their vendors natively consume `.apm`. Both OpenAPM [v0.1](https://microsoft.github.io/apm/specs/openapm-v01/#status-of-this-document) and the CLI's manifest [v0.3](https://microsoft.github.io/apm/reference/manifest-schema/#status-of-this-document) are editor's working drafts; the former explicitly disclaims backward compatibility before 1.0. Runtime APIs are out of scope, so build, execution and reconciliation remain external. |
| **Oracle Open Agent Spec** | Oracle ships real exporter/loader implementations for WayFlow, OpenAI Agents, Microsoft Agent Framework, LangGraph and AutoGen in the [26.3.1 cross-framework guide](https://oracle.github.io/agent-spec/26.3.1/howtoguides/howto_execute_agentspec_across_frameworks.html). | This is stronger than a schema-only proposal, but the documented adapters are all supplied by the Oracle project rather than independent vendor-owned consumers, and loading requires the caller to provide a tool registry. Its versioned release is credible implementation evidence, not proof that the interchange preserves every framework behavior or supplies deployment, secrets, state and reconciliation. |
| **Snap Agent Format** | Snap publishes a versioned [1.0 JSON Schema](https://agentformat.org/schema/1.0/agentformat-schema.json). Its launch article says Snap uses internal adapters for Google ADK, LangChain and PydanticAI plus its internal Auton SDK and Console ([first-party description](https://eng.snap.com/agent-format)). | The same article says only the specification is public and presents it as a proposed community answer. The claimed adapters and runtime are therefore not independently inspectable public integrations; a `1.0` schema label alone does not establish ecosystem adoption or operational portability. |
| **A2A Agent Card / OASF record** | A2A is a Linux Foundation protocol with a released [1.0.0 specification](https://a2a-protocol.org/v1.0.0/specification/) and official [Python, Go, Java, JavaScript, .NET and Rust SDKs](https://a2a-protocol.org/latest/sdk/). OASF publishes a versioned [agent-record schema and validator](https://docs.agntcy.org/oasf/agent-record-guide/), and its SDK implements a concrete [`RecordToA2A` conversion](https://github.com/agntcy/oasf-sdk/blob/main/USAGE.md). | This is the strongest governance/versioning and implementation story in the set, but at a different seam: A2A standardizes communication with an already running opaque agent, while OASF standardizes catalog/discovery metadata. Neither authors the persona or provisions the runtime described by its record/card. |

**Constrained recommendation:** if “one ready language” means a reusable **named agent description and instruction body**, use the GitHub/VS Code custom-agent Markdown shape (`.github/agents/<profile>.agent.md`) as the import/export profile and restrict the portable content to display name, description and Markdown instructions. That choice is based on the documented product surfaces above; the prediction that future controllers are more likely to import it than APM, Oracle or Snap is **inference**, not documented roadmap or popularity data. Treat the profile as content, not authority: do not promise portable `model` or `tools`, validate and translate target-specific policy, and enforce permissions outside the file. Give each profile an immutable opaque ID in a committed `metadata.agentId` string: GitHub [documents the `metadata` extension but says IDEs do not use it](https://docs.github.com/en/copilot/reference/custom-agents-configuration), so the ID is controller metadata rather than portable profile semantics. Never derive that ID from mutable display `name` or filename.

At the adjacent seams, retain `AGENTS.md` for repository policy and `SKILL.md` packages for reusable capabilities. Their independently documented consumers make them safer cross-vendor bets for those jobs, but promoting either to “the agent language” would erase the distinction between context, capability and persona. A2A/OASF should be generated for deployed discovery; richer APM, Oracle and Snap descriptors remain optional adapters until independent consumers and compatibility guarantees exist. None of these formats replaces the image, secret binding, mutable provider state or reconciliation boundary below.

Two plausible newer contenders do not change the recommendation. Open Agent Format labels itself [version 0.8.0 and explicitly says most platforms have not fully integrated it](https://openagentformat.com/), offering mapping guides instead. GitAgent publishes a [git-native agent runtime and source repository](https://github.com/open-gitagent/gitagent), but that proves its own implementation, not independent controller consumption of its repository shape. They are worth watching, not a stronger ready portability contract.

APM and Nix overlap only at **materialization**, not at their whole purpose. APM turns its primitives and locked package dependencies into target-native trees; its [lockfile](https://microsoft.github.io/apm/concepts/package-anatomy/#anatomy-of-apmymlockyaml) pins resolved package commits and content hashes. For the recommended reuse-first path, keep `.agent.md` as the canonical descriptive profile and let Nix validate/project its portable fields into the selected harness's native tree before packaging the runtime. Do not add APM as a second, drifting persona source. Choose APM instead only when its adapters or dependency model justify making `.apm/agents` the authoring source, and fetch locked dependencies as explicit build inputs rather than assuming network access inside a normal [sandboxed Nix build](https://nix.dev/manual/nix/stable/command-ref/conf-file.html#conf-sandbox). If reuse is not a requirement and one harness is permanently pinned, Nix may generate that harness's native files directly. APM's OpenAPM [v0.1](https://microsoft.github.io/apm/specs/openapm-v01/#status-of-this-document) and implemented manifest [v0.3](https://microsoft.github.io/apm/reference/manifest-schema/#status-of-this-document) remain working drafts, so do not make their evolution a prerequisite without using those benefits.

An image can contain binaries, local files, an entrypoint and non-secret defaults. It cannot by itself establish mutable state in Slack, Zulip, a model vendor or another external account system. **Proposed boundary:** bake only provider-neutral identity and secret *references* into the descriptor/image; let the reconciler or a provider-backed infrastructure tool create external identities when an API and credentials exist, then resolve credentials at runtime. Manual onboarding remains explicit where no supported API exists. Never bake provider credentials into the image.

**Conservative composition:** the existing `.github/agents/*.agent.md` profile collection is the only membership source; do not add an index that repeats the same list. Each committed profile carries its immutable opaque ID in `metadata.agentId`, while consumers that ignore unknown or IDE-only fields still see the portable description and instructions. Nix scans that collection, validates ID uniqueness, joins sparse operational bindings keyed by ID, emits the selected harness's native files and a per-agent image, and records the repository/profile revision with the published image digest. That digest is the substrate-neutral handoff to bare-metal Microsandbox or an optional Kubernetes adapter; a CRD is not required for the former. Nix expressions, CRDs and IaC layers must not duplicate or infer membership. This composes established tools at their documented seams rather than proposing another standard.
