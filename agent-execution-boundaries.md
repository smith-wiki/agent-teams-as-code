# Execution boundaries for the three OMP/Kata agents

> **Status: theoretical design.** No repository grant, MCP endpoint, Secret, Pod, or NetworkPolicy has been created or tested. All organization, repository, MCP, and Secret names below are illustrative. The three deployment files remain the roster; no universal agent schema or new controller is proposed.

Keep three layers distinct: committed files express desired state; OMP/ACP files configure this harness; Kubernetes mounts, process credentials, network policy, and provider-side grants enforce real access. `AGENTS.md`, a role prompt, or a tool declaration grants nothing.

## 1. Where each runtime environment is defined

Use the selected route's three files—`deploy/deployments/{triage,analyst,reviewer}.yaml` with `spec.template.spec`, **or** `deploy/sandboxes/{triage,analyst,reviewer}.yaml` with `spec.podTemplate.spec`—as the per-agent mapping, not both ([deployment routes](three-agents-kata-plan.md#two-k3s--kata-deployment-routes)). Each Pod template declares its image, `runtimeClassName`, `workingDir`, command, environment inputs, mounts, ServiceAccount, security context, and network-policy labels. Kubernetes defines these container fields, and volumes become part of its filesystem view ([Container API](https://kubernetes.io/docs/reference/kubernetes-api/core/pod-v1/#Container), [volumes](https://kubernetes.io/docs/concepts/storage/volumes/#how-volumes-work)).

**Proposed OMP adapter:** set `workingDir: /work/<agent>` and start `buzz-acp` with `BUZZ_ACP_AGENT_COMMAND=omp` and `BUZZ_ACP_AGENT_ARGS=acp,--config,/opt/omp/<agent>.yml`. That YAML is only an explicit OMP settings overlay; it is not auto-discovered and cannot define ACP cwd or MCP inventory ([OMP CLI](https://github.com/can1357/oh-my-pi/blob/04f58a91d141bb0e7c5f7679c2235945ae813057/docs/cli-reference.md#launch-flags), [ACP settings](https://github.com/can1357/oh-my-pi/blob/04f58a91d141bb0e7c5f7679c2235945ae813057/docs/approval-mode.md#acp-sessions)). Buzz supplies its absolute process cwd to ACP, so the Pod working directory must be the mounted workspace ([Buzz cwd source](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/crates/buzz-acp/src/lib.rs#L79-L95)). `roles/<agent>.md` remains guidance, not enforcement.

Run as non-root, disallow privilege escalation, drop unneeded capabilities, and use a read-only root plus explicit scratch space ([security contexts](https://kubernetes.io/docs/tasks/configure-pod-container/security-context/)). Kata adds a lightweight-VM Pod boundary, but does not restrict files, credentials, or destinations inside it ([Kata](https://github.com/kata-containers/kata-containers/blob/4.2.0/README.md#introduction), [RuntimeClass](https://kubernetes.io/docs/concepts/containers/runtime-class/)).

## 2. Where readable repositories are defined and enforced

Declare repositories in each deployment file as volume population and narrow credential references—not in role text. **Proposed enforcement:** only an init container receives a short-lived read token and fetches a pinned revision into an `emptyDir`; the OMP container mounts it `readOnly: true`. The checkout must contain no token in `.git/config`, remote URL, or files handed to OMP. Refresh-on-restart versus a repository reconciler remains open.

| Deployment | Role and runtime mounts | Desired MCP capability | Illustrative grants / Secret references |
|---|---|---|---|
| `triage.yaml` | `roles/triage.md`; `/work/triage/playbook` = `example/support-playbook`, read-only | `ticket-catalog`, read-only | GitHub token: only `support-playbook`, `contents: read`; separate triage MCP/Buzz/model refs |
| `analyst.yaml` | `roles/analyst.md`; `example/product-api` and `example/incident-archive`, read-only | `evidence-search`, read-only | Token limited to those two repositories; separate analyst MCP/Buzz/model refs |
| `reviewer.yaml` | `roles/reviewer.md`; `example/product-api` and `example/release-policy`, read-only | `ci-results`, read-only | Token limited to those two repositories; separate reviewer MCP/Buzz/model refs |

A GitHub App installation token can be narrowed to named repositories and a permission subset, uses `Contents` for HTTP Git access, and expires after one hour ([permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app#choosing-permissions-for-git-access), [tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app#generating-an-installation-access-token)). Let a broker/controller retain the App private key and mint init tokens; never give it to agents.

This scopes **private** GitHub access, not every readable URL: public repositories remain fetchable if outbound internet access is allowed. A read-only mount prevents modifying that checkout, not copying its contents or sending them elsewhere; provider grants and egress policy must match the intended data-access boundary.

## 3. Where MCP servers and tool gates are defined

At the pinned OMP revision, the ACP client exclusively owns MCP through `session/new.mcpServers`; OMP sets `enableMCP: false`, so `.omp/mcp.json` and ambient client configs are not discovered in `omp acp` ([OMP ACP factory](https://github.com/can1357/oh-my-pi/blob/04f58a91d141bb0e7c5f7679c2235945ae813057/packages/coding-agent/src/main.ts#L490-L539)). Native MCP JSON and `/mcp` slash commands apply to ordinary OMP sessions, not this path ([MCP guide](https://github.com/can1357/oh-my-pi/blob/04f58a91d141bb0e7c5f7679c2235945ae813057/docs/mcp-config.md)).

`buzz-acp` is the WebSocket-to-ACP-stdio bridge, not a business MCP server ([Buzz architecture](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/crates/buzz-acp/README.md#buzz-acp)). `BUZZ_ACP_MCP_COMMAND` currently emits zero or **one** argument-free stdio definition and gives that server the Buzz URL and private key ([source](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/crates/buzz-acp/src/lib.rs#L5872-L5920)). Thus the table records desired business MCP access, but safe delivery is an **open adapter requirement**. Do not invent `omp/<agent>.mcp.json`: adapt the ACP client to send per-agent definitions without unrelated secrets, or use one reviewed per-agent gateway. Several direct or HTTP/SSE servers require an adapted client. Buzz reply tooling is separate.

Each OMP overlay should deny unneeded built-ins and final MCP tool names. ACP requests fail closed when rejected or unsupported; explicit `yolo` skips prompts unless a per-tool `prompt` or `deny` remains. Approval is not filesystem, process, credential, or network containment ([ACP approval](https://github.com/can1357/oh-my-pi/blob/04f58a91d141bb0e7c5f7679c2235945ae813057/docs/approval-mode.md#acp-sessions), [warning](https://github.com/can1357/oh-my-pi/blob/04f58a91d141bb0e7c5f7679c2235945ae813057/docs/approval-mode.md#safety-overrides)); provider-side MCP scopes are authoritative.

## 4. Where secrets and network access are enforced

Commit only Secret references or, optionally, [External Secrets](https://external-secrets.io/latest/api/externalsecret/) desired state. Kubernetes Secrets are base64-encoded and unencrypted in etcd by default; enable at-rest encryption and least-privilege RBAC ([guidance](https://kubernetes.io/docs/concepts/security/secrets-good-practices/)). Set `automountServiceAccountToken: false` unless Kubernetes API access is required ([ServiceAccounts](https://kubernetes.io/docs/concepts/security/service-accounts/#assign-to-pod)).

`buzz-acp` spawns OMP without clearing the parent environment, removing only selected variables. OMP and approved arbitrary execution can therefore read `BUZZ_PRIVATE_KEY` and model secrets. Secret injection keeps values out of Git, not out of OMP; the optional Buzz MCP child also receives the key ([spawn](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/crates/buzz-acp/src/acp.rs#L464-L575), [MCP](https://github.com/block/buzz/blob/930b8bb800d8149ce29a881ba4c5d9f424580434/crates/buzz-acp/src/lib.rs#L5872-L5920)). Key isolation requires a signing broker/proxy or split bridge with sanitized IPC; the current parent/child launch cannot provide it. OMP profiles isolate persisted state, not inherited credentials.

Apply default-deny ingress/egress and allow only the required DNS, Buzz relay, model, MCP, and GitHub network destinations. NetworkPolicy needs an enforcing plugin, is additive L3/L4 policy, and cannot limit access to a specific GitHub repository or URL path; provider credentials enforce repository grants, and stricter destination controls require an egress proxy ([Kubernetes NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/), [k3s built-in controller](https://docs.k3s.io/networking/networking-services#network-policy-controller)). Exact endpoints, broker, token refresh, MCP adapter, and grants remain open.

When replacing OMP, retain the three-Pod topology, role files, repository access intent, Buzz identities, and network policy; update each workload's image/command and harness-native settings, MCP delivery, credentials, and approvals. ACP preserves the process seam, not those adapter details.
