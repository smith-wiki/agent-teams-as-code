# Choose the agent controller before its authoring language

**Operator-first correction:** provider-account provisioning and chat-specific event handling are not criteria for selecting an agent deployer. Kubernetes already has shipped controllers that instantiate agents: [kagent 0.x `Agent`](https://kagent.dev/docs/kagent/0.x/concepts/agents/) reconciles declarative or A2A-compatible BYO workloads, while [SIG Apps Agent Sandbox](https://github.com/kubernetes-sigs/agent-sandbox#readme) reconciles a generic container sandbox rather than an agent definition. Microsandbox exposes a host [CLI and SDK](https://github.com/superradcompany/microsandbox#readme) for creating guests, but no verified released Microsandbox controller for desired-state agent resources ([deployment boundary](microsandbox-kubernetes.md)). Select an actual controller and then author its input schema; the earlier full account/event design remains a separate question below.

## Documented boundaries

| Product | What it supplies — and what it does not |
|---|---|
| **Kubernetes / GitOps** | A controller watches desired state and reports observed state; a `Job` runs a finite Pod and may retry it. `Lease` objects can elect one controller leader, but neither Jobs nor Leases provide message exactly-once semantics ([controllers](https://kubernetes.io/docs/concepts/architecture/controller/), [Jobs](https://kubernetes.io/docs/concepts/workloads/controllers/job/), [Leases](https://kubernetes.io/docs/concepts/architecture/leases/)). Flux Receivers and Argo CD webhooks accelerate a Git refresh; their documented base behavior remains reconciliation or polling, not provider-event dispatch ([Flux receiver](https://fluxcd.io/flux/components/notification/receivers/), [Flux source interval](https://fluxcd.io/flux/components/source/gitrepositories/), [Argo CD](https://argo-cd.readthedocs.io/en/stable/operator-manual/webhook/)). |
| **Crossplane / External Secrets Operator (ESO)** | Crossplane can manage only resource kinds implemented by an installed provider. ESO fetches or generates values into a Kubernetes `Secret` and can refresh them periodically or on change; it does not thereby create a Slack app, mailbox or model-provider account ([providers](https://docs.crossplane.io/latest/packages/providers/), [ESO refresh](https://external-secrets.io/latest/api/externalsecret/)). Kubernetes Secrets also need encryption at rest and narrow RBAC because they are unencrypted in etcd by default ([Secrets](https://kubernetes.io/docs/concepts/configuration/secret/)). |
| **Existing agent operators** | Several shipped controllers reconcile agent workloads, but their APIs are not interchangeable. kagent 0.10.x and Agentic Layer create Kubernetes workloads from agent-shaped CRs; Kagenti’s current Rossoctl operator enrols an existing Deployment; LangSmith provisions its own Agent Server; kagent 1.0 alpha and Caliban add their own runtime layers. SIG Apps Agent Sandbox manages Pod-based sandboxes rather than agent semantics. None is a Microsandbox controller ([kagent BYO](https://kagent.dev/docs/kagent/0.x/examples/a2a-byo/), [Agentic Layer](https://docs.agentic-layer.ai/agent-runtime-operator/agents/reference.html), [Rossoctl](https://github.com/rossoctl/operator#readme), [LangSmith](https://docs.langchain.com/langsmith/deploy-with-control-plane), [Caliban](https://github.com/caliban-ai/caliban-operator#readme), [Agent Sandbox](https://github.com/kubernetes-sigs/agent-sandbox#readme)). |
| **Provider APIs** | Provisioning is possible only where the provider exposes a suitable admin API and the operator already has tenant authority. Slack supports manifest create/update/delete with a short-lived app-configuration token; Google Workspace exposes user creation, with mailbox licensing and setup still separate. Zulip documents admin-only user creation subject to plan/permission, while its bot-creation help flow is through the UI, so these identities must not be conflated ([Slack](https://docs.slack.dev/app-manifests/configuring-apps-with-app-manifests/#manifest_apis), [Google](https://developers.google.com/workspace/admin/directory/v1/guides/manage-users), [Zulip user API](https://zulip.com/api/create-user), [Zulip bot flow](https://zulip.com/help/add-a-bot-or-integration)). Billing, licensing, approvals and initial tenant-admin authority remain out of band. |

## Kubernetes operator-first decision

Choose the controller first, then author the resource that controller actually watches. A repository file is useful only if it compiles to that resource without erasing required runtime semantics. Provider-account creation and chat-specific event intake are separate concerns and are intentionally not selection gates here.

**Decision:** start with the 0.10.x kagent `Agent` CR when the agent can use kagent’s declarative runtimes or expose A2A. Prefer Agentic Layer when the desired state must directly include prompt/model/tools and a plain Deployment is acceptable; prefer SIG Apps Agent Sandbox when a generic agent container needs controlled sandboxed Pod lifecycle rather than agent semantics. For a hard per-agent Kata requirement, however, only Agent Sandbox exposes the required Pod field natively; the kagent and Agentic Layer qualifications are detailed below. Use Rossoctl only to enrol an already-owned workload, and LangSmith only when its licensed control plane is wanted. Treat kagent 1.0 as an explicit alpha/Substrate migration. Evaluate Caliban as specialized source code until its installation is productized. None of these schemas promises cross-vendor portability or deploys a Microsandbox guest.

AWS’s [`AWS::BedrockAgentCore::Runtime`](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-bedrockagentcore-runtime.html) is a credible declarative alternative outside this table: CloudFormation owns its artifact, IAM, network, environment and protocol in AWS AgentCore, not in Kubernetes. AOF publishes `Agent`, `Fleet` and `Trigger` CRDs but still labels its operator and installation “Future,” so it is a proposed API rather than a current controller ([AOF CRDs](https://docs.aof.sh/docs/reference/kubernetes-crds/)). The released [`kagents`](https://github.com/amcheste/kagents) operator is archived, and unreleased demos are not operational choices.

## kagent release split and authoring contract

For a new production evaluation, do not read the 1.x `Harness` API back into the current 0.x line. The current install path defaults to **0.10.2**, whose reconciled resource is `kagent.dev/v1alpha2 Agent`. A declarative agent places its model, system message, tools and skills in `spec.declarative`; a BYO agent places its image and Pod settings in `spec.byo.deployment` and must expose A2A ([agent concepts](https://kagent.dev/docs/kagent/0.x/concepts/agents/), [BYO example](https://kagent.dev/docs/kagent/0.x/examples/a2a-byo/)). Both become Deployment-based workloads. The separate 0.x `AgentHarness` is an optional Substrate integration for OpenClaw or Hermes and is not the schema for an ordinary BYO agent ([installation](https://kagent.dev/docs/kagent/0.x/introduction/installation/#enable-agentharness-support), [AgentHarness](https://kagent.dev/docs/kagent/0.x/concepts/agent-harness/)).

`kagent.yaml` is an optional developer-project input to the **CLI**, not the controller API. `kagent deploy` translates it into the `Agent` CR and supporting resources; `--dry-run` can emit those manifests for review and GitOps ([CLI reference](https://kagent.dev/docs/kagent/0.x/resources/cli/kagent-deploy/), [worked output](https://kagent.dev/docs/kagent/0.x/getting-started/local-development/#deploying-the-project-to-a-kubernetes-cluster)). The documented dry-run output includes Secret data sourced from the environment file, so do not commit that generated Secret; commit the `Agent` and use the repository’s existing secret-management path.

kagent **1.0.0-alpha3** is a clean-break architecture, not a newer spelling of the same resource. `Harness` selects exactly one of `kagent`, `codex`, `claude` or `byo` and sets workload/Substrate policy; `AgentTemplate` carries behavior; `AgentInstance` is a conversation created through kagent’s gRPC API and persisted outside Kubernetes. The `byo` contract is fixed A2A gRPC on port 80 plus HTTP readiness on 8081, and its Actors run under Agent Substrate’s gVisor class rather than Microsandbox ([core concepts](https://kagent.dev/docs/kagent/1.x/about/core-concepts/), [BYO contract](https://kagent.dev/docs/kagent/1.x/agents/bring-your-own-agent/), [sandbox classes](https://kagent.dev/docs/kagent/1.x/substrate-runtime/sandboxing/)). Adopt it only after accepting the alpha API, database and runtime boundary; there is no in-place 0.10.x database migration ([version support](https://kagent.dev/docs/kagent/1.x/reference/versions/)).

## k3s and Kata: neither semantic `Agent` CR can select the runtime

Kata has two separate prerequisites. The node's CRI must already have a Kata handler and the cluster must have a `RuntimeClass` whose `handler` names it; only then does a Pod select that class through `spec.runtimeClassName`. Omitting that field selects the node's default handler ([Kubernetes setup and usage](https://kubernetes.io/docs/concepts/containers/runtime-class/#setup)). `RuntimeClass` therefore does not install Kata on a k3s host. K3s documents custom containerd templates and a node-level `--default-runtime`, but its automatic alternative-runtime list does not include Kata; use the actual class and handler installed in this cluster rather than assuming that the name is `kata` ([k3s containerd configuration](https://docs.k3s.io/advanced#configuring-containerd), [runtime options](https://docs.k3s.io/cli/agent#container-runtime)).

There is consequently no honest kagent or Agentic Layer manifest excerpt that both authors a semantic agent and natively requests Kata; `runtimeClassName` is outside either published Agent schema and cannot reach the generated Pod, and an annotation alone does not select a runtime. Do not hand-patch the owned Deployment.

Two operator-independent fallbacks avoid fighting reconciliation:

1. A platform-owned mutating admission webhook can target Pod `CREATE`, require an explicit opt-in label, and set `/spec/runtimeClassName` to the cluster's real Kata class. kagent copies labels from `spec.declarative.deployment.labels` or `spec.byo.deployment.labels`; Agentic Layer copies `spec.podMetadata.labels`. This preserves their semantic Agent CRs, but the webhook service, TLS, failure policy and scoping are additional cluster infrastructure, not features of either operator ([Kubernetes admission webhooks](https://kubernetes.io/docs/reference/access-authn-authz/extensible-admission-controllers/#what-are-admission-webhooks)).
2. If Kata is deliberately the default handler on every node where these Pods can land, the omitted field uses Kata. kagent can also constrain those nodes through its supported `nodeSelector` and `tolerations`; Agentic Layer 0.28.1 exposes neither, so this fallback must be cluster-wide for its Pods or rely on separate admission/scheduling policy.

**Kata-specific recommendation:** if explicit per-agent runtime placement is non-negotiable, use SIG Apps Agent Sandbox and build each authored agent into a runnable image, accepting that Kubernetes then stores only the workload definition. If the prompt/model/tool description must remain a first-class CR, keep kagent Declarative as the preferred controller and make Kata selection a separately owned admission policy. Agentic Layer has the same runtime-class gap and fewer placement controls, so Kata does not improve its ranking.

## Earlier end-to-end proposal (not required to deploy agents)

The following design adds image publication, provider identity, chat events and sessions. It is preserved as a separate possible integration, **not** a requirement for choosing or installing kagent, Agentic Layer, or Agent Sandbox. Their documented CRDs and controllers, rather than this proposed contract, determine the agent deployment language.

### Proposed contract

The repository group is the **only complete membership list**. Each membership entry carries an opaque, committed `agentId` (for example a UUID) that is never derived from a display name or path; renames therefore preserve identity. Generated operational records contain only that ID, the source revision, descriptor digest, immutable OCI image digest, runtime limits, requested capabilities and provider-specific secret references. They do not copy the whole group.

The image recipe may use Nix directly or run APM during the build. That choice ends at one contract: for each `agentId`, the builder publishes a `BuildRecord(sourceRevision, descriptorDigest, imageDigest)`. A revision cannot become runnable until its descriptor digest is paired with the registry-returned OCI manifest/index `sha256:` digest; a Nix store hash is not that digest, and tags are never accepted by the dispatcher ([OCI descriptors](https://github.com/opencontainers/image-spec/blob/main/descriptor.md)).

### Three-loop flow

1. **Build:** a Git push that changes membership, an agent descriptor, APM lock state or Nix inputs starts CI. The builder materializes the harness, builds and publishes the OCI image, then records its digest. It neither provisions accounts nor starts an agent.
2. **Reconcile configuration and accounts:** a verified Git webhook queues the new revision; digest publication, a credential-rotation event and a periodic full resync queue the same idempotent reconcile key. The reconciler validates unique `agentId` values, compares desired provider bindings with observed remote IDs, calls only supported provider admin APIs, and writes `Ready` for the exact `(source revision, descriptor digest, image digest)` tuple.
3. **Accept events:** provider webhooks or pollers validate the provider identity and insert a durable inbox row keyed by provider event ID and `agentId`. This is separate from GitOps refresh.
4. **Dispatch a session:** a dispatcher claims a renewable per-message lease and, when ordering matters, a per-conversation mutex. It pins the current `Ready` tuple on the session row and cold-starts a uniquely named Microsandbox guest from that digest. The host adapter persists the sandbox’s opaque stable ID before issuing commands. After an uncertain create, it lists/gets and adopts only an exact session-ID, image-digest and provider-binding match; a retry otherwise fails closed ([handle identity](https://docs.microsandbox.dev/sdk/python/sandbox#sandboxhandle)).
5. **Commit before acknowledgement:** the runner durably writes the provider cursor and result/outbox, then attempts to stop and remove the guest, records `Succeeded`, `Failed` or `CleanupBlocked`, and only then acknowledges the inbox event. Provider APIs without idempotency still imply at-least-once external delivery; the outbox can detect and surface ambiguity but cannot manufacture exactly-once behavior.

Microsandbox’s host proxy can substitute a secret only for allowed endpoints while keeping the value out of the guest, but the real value still exists in trusted host memory. Raw SDK values also persist in host-side sandbox configuration, so the dispatcher should resolve that agent’s capability-scoped secret references just in time, use host-environment references and narrow host allowlists, and remove the sandbox after the session ([secret boundary](https://docs.microsandbox.dev/security/secrets)).

### Placement and state ownership

| Process | Exact start/trigger | Bare metal | Kubernetes | Durable owner |
|---|---|---|---|---|
| **Image builder/publisher** | One finite run per relevant Git revision or explicit rebuild | CI runner or a systemd oneshot | Build `Job` in a separate builder pool | OCI registry plus append-only `BuildRecord`; never the guest |
| **Configuration/account reconciler** | Starts at host/cluster boot and stays running; Git/digest/rotation notifications enqueue work; timer rechecks all agents for drift | Supervised systemd service, or Nomad `service` job | Operator `Deployment`; one active reconciler elected with a Kubernetes `Lease` | Desired membership in Git; sparse observed status and immutable provider IDs in a transactional control-plane DB, or CR `status` on Kubernetes |
| **Event/session dispatcher** | Starts at boot; consumes only authenticated provider events or configured polling results | systemd or Nomad `service` job | `Deployment`; replicas claim rows in the shared database | Inbox, leases, pinned session revision, conversation cursor, result and outbox in PostgreSQL (SQLite is acceptable only for a single host); large payloads/results in object storage |
| **Session runner** | Starts only after a message lease is won; exits after result commit or timeout | `systemd-run` transient unit or dispatched Nomad `batch` job | One `Job` on a KVM-capable worker; the Job Pod is the host-side adapter that creates the Microsandbox guest, not the guest itself | No authoritative state; it checkpoints through the dispatcher store |
| **Credentials** | Created/rotated only by an authorized provider adapter or human gate | Vault/cloud secret manager; the service receives a reference or short-lived value | Same external store; ESO may project an already-authorized value into a narrowly scoped Secret | Secret manager owns values and versions; the operational record stores only a provider-specific reference and rotation metadata |

Systemd directly supervises long-running and transient services; Nomad supplies service and batch schedulers and rescheduling policies ([systemd service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html), [Nomad jobs](https://developer.hashicorp.com/nomad/docs/job-specification/job), [rescheduling](https://developer.hashicorp.com/nomad/docs/job-specification/reschedule)). On Kubernetes, Job retries make the database lease, unique provider event key and durable outbox mandatory rather than optional. The Microsandbox host adapter and all control-plane code stay outside the ephemeral guest in both placements; Kubernetes nodes must follow the repository’s [KVM-capable deployment path](microsandbox-kubernetes.md).

### Fail-closed reconciliation rules

- **Provider onboarding:** every adapter declares `Observe`, `Create`, `Update`, `Rotate`, `Disable` and `Delete` support independently. Where a Crossplane provider implements the resource, bind it to an explicit provider account configuration rather than an implicit default. Missing API, missing admin scope, interactive consent, licensing or approval sets `ManualActionRequired`; the corresponding capability remains unavailable and the dispatcher refuses events that require it. Secret synchronization is not evidence that the account exists.
- **Credentials:** give every `agentId` a distinct remote app/account where the provider permits it, a least-privilege workload principal and a distinct secret path. Rotation writes a new secret version, proves the new credential, switches the reference and only then revokes the old one. Failure keeps the binding not-ready rather than falling back to a group credential.
- **Conflicts and adoption:** duplicate `agentId`, one remote ID claimed by two agents, an image/descriptor mismatch, or a remote object whose ownership cannot be proven is `Conflict` and blocks execution. Adoption requires an explicit immutable remote ID plus an administrative approval and successful observation; never adopt by display-name matching.
- **Drift:** reconcile only fields the adapter declares authoritative and mutable. Unsupported or immutable drift becomes a condition for human resolution; do not silently delete and recreate. Crossplane likewise treats declared fields as authoritative but does not replace an external resource merely because an immutable field changed ([managed resources](https://docs.crossplane.io/latest/managed-resources/managed-resources/)).
- **Deletion:** absence from an invalid or not-yet-built revision is never a delete signal. A committed tombstone first disables event intake and drains or expires session leases. Revoke credentials, then delete a remote object only when policy is `Delete`, the adapter supports deletion, and the stored ID plus provider-side ownership marker both match; otherwise retain it as `Orphaned`. Keep the tombstone—and, on Kubernetes, its finalizer—until observation confirms absence; acceptance of an asynchronous delete request is not completion ([finalizers](https://kubernetes.io/docs/concepts/overview/working-with-objects/finalizers/)).
