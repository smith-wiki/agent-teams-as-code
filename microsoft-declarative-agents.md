# Microsoft “declarative agents” are runtime and app definitions, not APM packages

These offerings occupy three different layers despite similar names.

**Microsoft Agent Framework** can construct and run an agent from YAML or JSON. Its documented prompt-agent example uses `kind: Prompt`, `name`, `description`, `instructions`, `model` and `outputSchema`; persona/role belongs in `instructions`, not a separate `role` field. The host supplies the chat client and credentials, then calls the resulting agent ([declarative agents](https://learn.microsoft.com/en-us/agent-framework/agents/declarative)). Workflows are a separate executable YAML DSL. C# uses `kind: Workflow` plus an `OnConversationStart` trigger; Python uses `name`, optional `inputs`, and `actions`. Actions cover control flow, `InvokeAzureAgent`, function/MCP tools, HTTP, human input and conversation control ([declarative workflows](https://learn.microsoft.com/en-us/agent-framework/workflows/declarative)). The runtime can store checkpoints and resume execution for fault tolerance, even on another machine. That is persistence, not an evidenced idle-time sleep/wake scheduler. Credentials, tool handlers and checkpoint storage remain host responsibilities; the YAML does not provision identities or turn declared tools into enforced account grants.

**Microsoft 365 Copilot declarative agents** are tenant-distributed apps, not general Agent Framework definitions; Copilot runs them on its orchestrator. The published v1.8 JSON Schema requires `version`, `name` and `description`; it permits `instructions`, `capabilities`, `conversation_starters`, plugin `actions` and `worker_agents` ([schema](https://developer.microsoft.com/json-schemas/copilot/declarative-agent/v1.8/schema.json)). (The accompanying [Learn property table](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/declarative-agent-manifest-1.8) calls `instructions` required, but the linked machine-readable schema does not.) Preview `worker_agents` lets one agent refer to other published declarative agents, a platform-specific composition feature, not lifecycle management ([worker-agent contract](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/declarative-agent-manifest-1.8#worker-agent-object)). A manifest is referenced by `copilotAgents.declarativeAgents` in a Microsoft 365 app package; logic and storage can live elsewhere ([app model](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/agents-are-apps)). Capability declarations select platform integrations, but documented data access remains bounded by what the user can access, licensing/metering and tenant controls. Admin approval/deployment governs organizational availability ([publishing](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/publish)); the manifest does not create employee accounts, mailboxes or host ACLs, and its schema documents no sleep lifecycle.

**Fit:** use Agent Framework when this system should execute agents/workflows; use a Microsoft 365 manifest for a Copilot app in a tenant. Use **APM** to install, lock and compile reusable agent configuration; its own boundary is explicit: “your agent harness governs what runs” ([APM](https://github.com/microsoft/apm)). None replaces an identity reconciler or a sleep-capable coordinator.
