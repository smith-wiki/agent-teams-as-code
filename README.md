# Agent groups as code

How to describe a repository-scoped group of independent agents—roles, tools, enforced access, communication identities—and operate onboarding plus event-driven, suspendable execution.

## Questions and answers

1. **How can I define agents declaratively and handle onboarding and sleeping?** **Revised:** keep [per-agent definitions in the repository](agent-manifest.md); [APM](microsoft-apm.md) is an optional packaging adapter, while [Nix can build one chosen harness's image](agent-language-options.md). No separate team object is needed. Reconcile each agent's communication accounts and grants ([identity reconciliation](identity-reconciliation.md)); a coordinator owns events and sessions ([sleeping agents](sleeping-agents.md)). **Open:** confirm whether “Buzz” means [Block's Buzz](https://github.com/block/buzz); full mailboxes and other provider-specific grants remain undecided.

2. **Was the missing Microsoft tool called APM, and does it solve this?** Yes: [Microsoft Agent Package Manager](microsoft-apm.md) installs/version-pins agent files, instructions, skills and MCP servers across supported harnesses. It can launch shell scripts, but does not provision communication accounts or manage sleeping sessions. [Microsoft Agent Framework and Microsoft 365 declarative agents](microsoft-declarative-agents.md) are separate runtime/product-specific formats. This [corrects the earlier comparison](descriptor-landscape.md).

3. **Do we need a distinct team object, or a group of agents in one repository?** Just the [repository-scoped group](agent-manifest.md). An APM package can contain multiple `.apm/agents/*.agent.md` files; `apm.yml` describes the package, not shared team behavior. Do not author an `AgentTeam` or duplicate the file list unless explicit membership beyond the repository becomes a requirement. Accounts, grants and runtime state belong to individual agents and their operators.

4. **Who deploys agents from the repository, where do they run, and does APM handle onboarding?** A developer or deployment job invokes [APM installation](apm-install-deployment.md) in a target workspace: it projects agent files and MCP settings to the selected harness, not to a remote running service. APM can [scaffold the project, install some runtime CLIs, run a shell script and offer trusted install hooks](apm-onboarding-runtime.md), but it neither creates provider accounts/grants nor hosts event-driven sessions. The execution hosts are now known to be either a Kubernetes cluster or bare-metal Linux; the agent harness is still unspecified.

5. **How would these agents run inside microsandbox on bare metal or Kubernetes?** On [bare metal](microsandbox-bare-metal.md), a KVM-capable Linux host boots an OCI image with an agent harness; the guest receives the APM package and can select a named profile (for example, `opencode run --agent reviewer`). In [Kubernetes](microsandbox-kubernetes.md), a KVM-capable node must expose that device to a worker Pod running microsandbox; this is not a built-in team deployment. External coordination must own events and durable state in either case.

6. **Can I define the agent group in a portable language, then automatically deploy it with accounts and credentials?** [APM is the practical authoring/package layer](agent-language-options.md), but its agent files do not specify operational identities or launch independent processes. A [deployment and identity control plane](agent-control-plane-options.md) must map each agent to an image, reconcile provider-specific accounts where APIs permit, store credentials outside Git, and start its isolated runtime. No verified product implements this entire APM-to-microsandbox-to-provider-account path without an integration layer. Kubernetes kagent offers a closer integrated alternative if its own gVisor-based runtime can replace microsandbox; it still requires pre-created external credentials.

7. **Does APM recommend a way to launch and operate these agents?** Its [documented path](apm-onboarding-runtime.md) is to install role files into a supported harness and invoke them there; `apm run` optionally executes a named, foreground shell script and `apm runtime setup` installs selected CLI binaries. Neither starts one persistent worker per `.agent.md` nor provisions its external identity. For independent unattended agents, a separate runner must select each harness invocation, supply its workspace and credentials, and manage events, scheduling and state. An experimental local Copilot App scheduled-prompt integration is not a general cluster runtime.

8. **What is APM, and what does it take in and produce?** APM is a [package manager and target adapter for agent configuration](microsoft-apm.md#input-and-output). It reads `apm.yml`, authored `.apm/` primitives, dependency packages, the chosen harness targets and optionally a lockfile; `apm install` writes harness-specific agent/configuration files, a lockfile and installed dependencies. The output is not a running agent or its response to a task. The harness and its operator supply execution separately.

9. **Which agent harnesses does APM support? Is there a list?** The official [targets matrix](https://microsoft.github.io/apm/reference/targets-matrix/) lists APM output targets, **not exclusively harnesses**. Named agent files deploy to Copilot, Claude Code, Grok Build, Cursor, Codex, OpenCode and Kiro; Gemini, Antigravity, Windsurf and Hermes accept other primitives but not agent files. The [`intellij` and `agent-skills` entries are integrations, not harnesses](microsoft-apm.md#harnesses-and-other-apm-targets). Run `apm targets` to inspect project targets, or select explicitly with `apm install --target opencode`.

10. **Why was IntelliJ included in a list of agent harnesses?** It should not have been. The [APM target taxonomy](microsoft-apm.md#harnesses-and-other-apm-targets) includes an `intellij` adapter for MCP configuration in GitHub Copilot's JetBrains IDE integration; agent files still follow the Copilot profile. IntelliJ is the host IDE, not an independent agent harness or runtime.

11. **Can we use APM only as the description language, not as a reconciler?** Almost: APM is also a [dependency resolver and installer](microsoft-apm.md#input-and-output) that projects configuration into harness-native files and updates those files when invoked. It is **not** an operator that continuously reconciles agent instances, isolation, events, external accounts, or credentials. Use it for authoring and materialization, with a separate operational controller for those states.

12. **Can I build a Docker image from the APM description just by running `apm install`?** [During an image build](apm-install-deployment.md#building-a-container-image), copy the APM package and lockfile into the build context, then run `apm install --target opencode --frozen` to bake harness-specific role/configuration files into the image. That works for configuration, not the complete runtime: provide the base image, harness executable and invocation separately, and inject credentials when the container runs. `apm install` does not produce a runnable agent or choose its startup command.

13. **If Nix can build the image, which description languages fit the design, and where and when does reconciliation run?** [Role languages and build DSLs solve different layers](agent-language-options.md): APM is optional when Nix packages one harness's native agent files; a small validated per-agent operations contract must still describe required identities and runtime bindings. A separate [control plane](agent-control-plane-options.md), installed once outside the agent sandbox, reacts to approved repository releases and periodic drift checks to reconcile accounts, permissions and image bindings. An event coordinator then leases each incoming task and starts its agent only when needed. Keep desired definitions in Git, observed provider IDs and task state in durable storage, and secret values in a secret manager—not in the image.

14. **Would kagent supply the reconciler and runtime instead?** **Revised:** yes, for Kubernetes: the released [kagent 0.10.x `Agent` controller](agent-control-plane-options.md#kubernetes-operator-first-decision) reconciles declarative and A2A-compatible BYO agents into Deployments. Its separate 0.x `AgentHarness` is for OpenClaw/Hermes; [1.x `Harness`/`AgentTemplate` is an incompatible alpha/Substrate path](agent-control-plane-options.md#kagent-release-split-and-authoring-contract). Neither deploys a Microsandbox guest. Provider accounts and event ingestion are distinct later concerns, not a prerequisite to selecting this deployer.

15. **Which existing agent-description language should we choose for maximum reuse by a future reconciler, and is there already a complete operator?** The earlier [`.agent.md` profile comparison](agent-language-options.md#which-existing-language-is-the-safest-reuse-bet) applies only when sharing named instruction profiles among coding clients. It does not establish a future controller's input, and accounts/events are not a useful criterion for selecting an agent deployer. **Superseded for deployment by question 16:** choose a shipped controller first, then its own CRD or runtime configuration.

16. **Can we set chat-specific accounts and event wake-up aside, find actual Kubernetes or Microsandbox agent deployers first, and only then choose the authoring language?** Yes. [kagent 0.10.x](agent-control-plane-options.md#kubernetes-operator-first-decision) reconciles a semantic `Agent` into a Deployment for general Kubernetes; [SIG Apps Agent Sandbox](microsandbox-kubernetes.md) reconciles a generic Pod-based `Sandbox`. Neither deploys a superradcompany Microsandbox guest. **Resolved:** the target is now k3s with Kata Containers, not Microsandbox; the generic-kagent recommendation does not establish Kata placement. See question 17 for the stricter runtime constraint.

17. **Can my authored agent descriptions become running agents inside Kata microVM-backed Pods on k3s?** [Agent Sandbox v1.0.4](microsandbox-kubernetes.md#k3s-and-kata-a-real-pod-sandbox-not-an-agent-definition) natively reconciles a Pod with `spec.podTemplate.spec.runtimeClassName` set to the installed Kata class, but does not interpret prompts, models or tools. Supply an executable agent harness image configured from those descriptions, then apply its `Sandbox`. [kagent 0.10.2 and Agentic Layer 0.28.1](agent-control-plane-options.md#k3s-and-kata-neither-semantic-agent-cr-can-select-the-runtime) interpret semantic `Agent` descriptions but their generated Pods have no configurable runtime class; requiring Kata with either also requires an explicitly owned Pod-admission policy or node-level default. No reviewed controller directly provides *both* description-to-agent semantics and per-agent Kata selection. [The input layers](agent-language-options.md#from-an-agent-description-to-a-kata-backed-process) stay distinct. **Open:** the existing description format and intended harness determine the safe conversion into a working image or agent CR.

For the settled k3s + Kata target, start with the [verified operator/runtime comparison](agent-control-plane-options.md#k3s-and-kata-neither-semantic-agent-cr-can-select-the-runtime), the [Kata-backed Sandbox resource and prerequisites](microsandbox-kubernetes.md#k3s-and-kata-a-real-pod-sandbox-not-an-agent-definition), and [description-to-runtime inputs](agent-language-options.md#from-an-agent-description-to-a-kata-backed-process). These are sourced deployment options, not an installation in the user's cluster.

18. **What would a repository with three agents look like, how would I grant them Buzz identities, and how could I run three Kata Pods on k3s?** **Corrected after question 19:** the [three-agent deployment proposal](three-agents-kata-plan.md) keeps triage, analyst and reviewer independent, uses three Buzz identities, and selects a Kata RuntimeClass for three Pods via either Agent Sandbox or Deployments. The earlier answer wrongly hard-wired OpenClaw because it had a Buzz plugin; that is not a requirement of Buzz or the cluster.

19. **Why choose OpenClaw when I use OMP, and can I change the harness later?** Choosing OpenClaw was a mistaken connector-driven architecture decision. [Buzz's ACP bridge](https://github.com/block/buzz/blob/main/crates/buzz-acp/README.md#using-any-acp-agent) accepts any ACP-speaking agent, while [OMP implements `omp acp`](https://github.com/can1357/oh-my-pi/blob/main/docs/cli-reference.md). The [revised three-agent plan](three-agents-kata-plan.md) starts with OMP and keeps roles, Buzz identities, and Kata Pod placement independent of the ACP harness executable and its native configuration. This is an interface-level path, not a live-tested OMP–Buzz deployment.

20. **Where are these agents' environments, readable repositories, MCP servers, and secrets specified?** The [execution-boundaries card](agent-execution-boundaries.md) separates committed per-agent deployment intent from enforcement: images and Pod templates define runtime files and mounts; scoped Git credentials and mounted repositories determine private code access; provider credentials enforce MCP authority. **OMP in ACP mode does not load its usual MCP files**: Buzz's bridge can supply one stdio server, so additional business MCP access requires an adapter or gateway. Commit Secret references, never values; values may be projected into Pods, where OMP currently inherits the Buzz key. **Open:** choose the real repositories, MCP services, secret store, and key-isolation requirements.
