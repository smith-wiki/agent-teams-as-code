# Kubernetes: no shipped Microsandbox operator yet

**Verdict (checked 2026-09-26): no.** There is no currently usable first- or third-party Kubernetes controller that accepts an agent or sandbox resource and reconciles a **Microsandbox guest**. The vendor-owned [`microsandbox-k8s` repository at its only observed commit](https://github.com/superradcompany/microsandbox-k8s/tree/27dcb62c8d9ca768f186e9c0f78ebe61dcdf06d7) contains only `.gitignore` and `LICENSE`: no controller, CRD, manifests, chart, or documentation, and its [tags](https://github.com/superradcompany/microsandbox-k8s/tags) and [releases](https://github.com/superradcompany/microsandbox-k8s/releases) are empty. This corrects the older, stronger claim that no first-party repository exists; a placeholder now exists, but it is not installable software. This public-source check cannot exclude private or unindexed code or establish a future roadmap.

**What Microsandbox actually ships.** The observed current release is [`v0.7.3`](https://github.com/superradcompany/microsandbox/releases/tag/v0.7.3), while upstream still labels the project beta and says local embedding needs no setup server or long-running daemon ([tagged README](https://github.com/superradcompany/microsandbox/blob/v0.7.3/README.md)). Its local CLI and SDK create a child-process microVM from an OCI image and workload settings ([SDK model](https://docs.microsandbox.dev/sdk/overview)); they do not instantiate an agent framework, so the harness is bring-your-own through the image, command, environment, and scripts. CLI YAML is explicitly supplied with `--conf` and can set fields such as `image`, `cpus`, `memory`, `workdir`, mounts, network policy, secrets, and scripts ([configuration schema](https://docs.microsandbox.dev/cli/configuration)). The CLI provides named `create`, `start`, `stop`, and `rm` operations, while SDK applications call the sandbox lifecycle API ([lifecycle](https://docs.microsandbox.dev/sandboxes/lifecycle)). This is an imperative creation surface, not a reconciled resource: resolved settings are persisted at creation, and editing YAML changes only future sandboxes unless the operator separately invokes supported `msb modify` operations ([configuration semantics](https://docs.microsandbox.dev/operations/configuration)).

## k3s and Kata: a real Pod sandbox, not an agent definition

**Controller behavior is verified at `v1.0.4`.** Install the pinned core release from [`sandbox.yaml`](https://github.com/kubernetes-sigs/agent-sandbox/releases/download/v1.0.4/sandbox.yaml). The exact selection field is `Sandbox.spec.podTemplate.spec.runtimeClassName`: `podTemplate.spec` is a Kubernetes `PodSpec` in the [tagged API type](https://github.com/kubernetes-sigs/agent-sandbox/blob/v1.0.4/api/v1beta1/sandbox_types.go#L210-L218), and `runtimeClassName` is present in the [released CRD schema](https://github.com/kubernetes-sigs/agent-sandbox/blob/v1.0.4/k8s/crds/agents.x-k8s.io_sandboxes.yaml#L2927-L2928). This is not merely accepted and discarded: on Pod creation the controller deep-copies the complete template spec and assigns it to the backing Pod ([controller source](https://github.com/kubernetes-sigs/agent-sandbox/blob/v1.0.4/controllers/sandbox_controller.go#L1505-L1529)), so `runtimeClassName` reaches the kubelet.

**Kata is a node prerequisite, not something this controller installs.** Kubernetes resolves a Pod's `runtimeClassName` through a cluster-scoped `RuntimeClass`; its `handler` must name a CRI runtime configured on every eligible node, and heterogeneous clusters should constrain placement with `RuntimeClass.scheduling.nodeSelector` ([Kubernetes RuntimeClass setup and scheduling](https://kubernetes.io/docs/concepts/containers/runtime-class/)). K3s does not document Kata in its automatically detected runtime list. Its generated containerd file is `/var/lib/rancher/k3s/agent/etc/containerd/config.toml`; custom configuration belongs in the same directory as `config-v3.toml.tmpl` for containerd 2.0 or `config.toml.tmpl` for containerd 1.7 and earlier, extending K3s's base template rather than editing the generated file ([K3s containerd configuration and version gate](https://docs.k3s.io/advanced#configuring-containerd), [documented auto-detection list](https://docs.k3s.io/advanced#alternative-container-runtime-support)). For a manual installation, Kata `4.2.0` documents the matching containerd handler tables as `plugins."io.containerd.cri.v1.runtime".containerd.runtimes.kata` for containerd 2.x or `plugins."io.containerd.grpc.v1.cri".containerd.runtimes.kata` for 1.7.x, with `runtime_type = "io.containerd.kata.v2"` and an optional `options.ConfigPath` ([tagged Kata/containerd guide](https://github.com/kata-containers/kata-containers/blob/4.2.0/docs/how-to/containerd-kata.md#kata-containers-as-a-runtimeclass)). Alternatively, the pinned Kata Deploy `4.2.0` chart explicitly supports `k8sDistribution: k3s` and derives the K3s config directory and CRI socket; use `--set k8sDistribution=k3s` rather than assuming the chart's default `k8s` layout ([tagged chart values](https://github.com/kata-containers/kata-containers/blob/4.2.0/tools/packaging/kata-deploy/helm-chart/kata-deploy/values.yaml#L286-L317)).

The node must be bare metal or expose nested virtualization. Run `kata-runtime check` on each selected node; Kata `4.2.0` lists only 64-bit platforms and architecture-specific facilities: x86-64 needs Intel VT-x or AMD SVM, arm64 needs ARM Hyp, while ppc64le and s390x use their platform virtualization technologies ([installation prerequisite](https://github.com/kata-containers/kata-containers/blob/4.2.0/docs/install/README.md#prerequisites), [platform and hardware checks](https://github.com/kata-containers/kata-containers/blob/4.2.0/README.md#platform-support)). Do not label a node eligible until its architecture-matched Kata artifacts, hypervisor, KVM/nested-virtualization path, containerd handler, and a plain test Pod using that RuntimeClass all work.

This minimal resource is valid against the released `v1.0.4` schema and creates a long-running Kata-backed Pod. It assumes a `RuntimeClass` object named `kata` whose `handler: kata` is already wired to containerd, as in Kata's [tagged Kubernetes example](https://github.com/kata-containers/kata-containers/blob/4.2.0/docs/how-to/how-to-use-k8s-with-containerd-and-kata.md#create-runtime-class-for-kata-containers):

```yaml
apiVersion: agents.x-k8s.io/v1beta1
kind: Sandbox
metadata:
  name: kata-container-smoke
spec:
  podTemplate:
    spec:
      runtimeClassName: kata
      containers:
        - name: workload
          image: busybox:1.36.1
          command: ["sh", "-c", "while true; do sleep 3600; done"]
```

If Kata Deploy `4.2.0` is used with its defaults, it creates shim-specific classes such as `kata-qemu-runtime-rs` and leaves the short `kata` alias disabled (`runtimeClasses.createDefault: false`); either use the installed class name in the field above or deliberately enable that alias ([tagged defaults](https://github.com/kata-containers/kata-containers/blob/4.2.0/tools/packaging/kata-deploy/helm-chart/kata-deploy/values.yaml#L1019-L1039)). The result is a Kata-backed **Pod**, not a superradcompany Microsandbox guest. It is also not an agent-defining controller: `Sandbox` has no role, system-prompt, model, or tool semantics. Replace the smoke image with an agent harness image (and supply its configuration, credentials, prompt, and tools through normal Pod mechanisms); the controller only reconciles the workload and lifecycle.

**Recommendation for k3s + Kata:** use Agent Sandbox `v1.0.4` as the reconciled singleton-Pod lifecycle layer only after a direct Pod smoke test has proved the chosen Kata RuntimeClass on every eligible node. Put the authored role, prompt, model client, and tools in the harness image or its mounted configuration. If the desired resource itself must interpret those agent concepts, choose an agent-semantic controller instead; `Sandbox` alone is the wrong API.

**Nearest Kubernetes path and missing adapter.** Agent Sandbox is the nearest shipped controller, but selecting Kata or gVisor for its Pod does not create a Microsandbox guest. The released [Cocoonstack sandbox-operator `v0.1.4`](https://github.com/cocoonstack/sandbox-operator/releases/tag/v0.1.4) demonstrates a third-party backend seam, but its documented `standard`, `vk-cocoon`, and `sandboxd` backends target Pods or Cocoon's own runtime—not Microsandbox ([backend contract](https://github.com/cocoonstack/sandbox-operator/blob/v0.1.4/docs/runtime-backends.md)). A real Microsandbox integration still needs a controller/provider that translates desired resources into Microsandbox CLI/SDK operations on `/dev/kvm` hosts and reconciles guest identity, status, updates, deletion, storage, and recovery. An outer KVM-enabled Pod can instead run a custom `msb` worker ([official Docker/KVM example](https://docs.microsandbox.dev/examples/docker/docker)), but Agent Sandbox would reconcile only that Pod; the custom worker remains responsible for the nested guest and its drift.

**Operator choice:** if Microsandbox itself is mandatory, use its local bare-metal lifecycle and own the adapter, or evaluate Workestrate's unreleased declarative CLI. If Kubernetes-native reconciliation is mandatory, Agent Sandbox is usable now for Pod/RuntimeClass sandboxes, not Microsandbox. Do not choose or promise a portable authoring schema first: the shipped controller's `Sandbox` CRD, Microsandbox's create-time YAML, and Workestrate's TOML describe different resources and lifecycle owners.
