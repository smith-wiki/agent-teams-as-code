# Kubernetes: possible as a custom host placement, not a built-in integration

**Support boundary.** Kubernetes can wrap the documented Linux-in-Docker setup, but this is an operator-built deployment of the **local** backend: the official example requires usable `/dev/kvm` in the container and explicitly says it is not a cloud workflow ([Docker example](https://docs.microsandbox.dev/examples/docker/docker), [image recipe](https://github.com/superradcompany/microsandbox/blob/main/packaging/docker/Dockerfile)). Inspection of the complete [documentation index](https://docs.microsandbox.dev/llms.txt) and [upstream tree](https://api.github.com/repos/superradcompany/microsandbox/git/trees/main?recursive=1) finds no first-party Kubernetes manifests, Helm chart, operator/controller, CRD or BYOC installer. The only documented ready-to-use remote option is hosted cloud; a configurable self-hosted/on-prem API URL is a client setting, not an installer ([cloud](https://docs.microsandbox.dev/cloud/overview), [backends](https://docs.microsandbox.dev/operations/backends#profiles)).

**Node and Pod prerequisites.** Select Linux nodes with read/write `/dev/kvm` and nested virtualization when the node is itself a VM; the container image running microsandbox must also satisfy its glibc 2.28+ requirement. Label verified nodes and require that label with `nodeSelector` or node affinity ([Linux requirements](https://docs.microsandbox.dev/troubleshooting/linux), [node assignment](https://kubernetes.io/docs/concepts/scheduling-eviction/assign-pod-node/)). Prefer a KVM device plugin: Kubernetes device plugins advertise an extended resource, constrain scheduling, and inject device nodes; with KubeVirt installed, request the limit `devices.kubevirt.io/kvm: 1` ([device plugins](https://kubernetes.io/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/), [KubeVirt example](https://kubevirt.io/2018/KVM-Using-Device-Plugins.html)). The fallback—`hostPath` `/dev/kvm` (`type: CharDevice`) plus runtime-specific privileges, often `privileged: true`—is a cluster exception, not Docker’s narrow `--device`: Kubernetes warns that `hostPath` is risky, Baseline Pod Security forbids `hostPath` and privileged containers, and privileged mode disables kernel controls ([volumes](https://kubernetes.io/docs/concepts/storage/volumes/#hostpath), [Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/), [privileged containers](https://kubernetes.io/docs/concepts/security/linux-kernel-security-constraints/#privileged-containers)).

**Proposed topology.** Build an outer worker image containing the microsandbox CLI/SDK and queue consumer, **not** the agent harness. The worker creates local sandboxes from a separate guest OCI image containing the harness; install the repository’s APM package into each guest workspace or prepare its files at image-build time. Each actual agent runs in a guest microVM with its own kernel ([SDK model](https://docs.microsandbox.dev/sdk/overview), [isolation boundary](https://docs.microsandbox.dev/security/isolation), [bare-metal handoff](microsandbox-bare-metal.md)). Use one Job per bounded task, or one long-lived worker Pod per leased agent. Jobs may replace failed Pods, so delivery/result publication must be idempotent ([Jobs](https://kubernetes.io/docs/concepts/workloads/controllers/job/)).

Mount a dedicated PVC at `/root/.microsandbox` (or configured `MSB_HOME`) to preserve images, stopped sandboxes, snapshots and SQLite; do not concurrently share one home between workers ([Docker persistence](https://docs.microsandbox.dev/examples/docker/docker#persist-images-and-sandboxes)). A local PV requires `nodeAffinity`; `WaitForFirstConsumer` coordinates it with KVM placement, but node failure makes state unavailable ([local volumes](https://kubernetes.io/docs/concepts/storage/volumes/#local)). Pod replacement is not VM live migration and may land elsewhere; persist outputs/checkpoints externally and stop or snapshot during graceful termination ([Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/), [Microsandbox lifecycle](https://docs.microsandbox.dev/sandboxes/lifecycle), [snapshots](https://docs.microsandbox.dev/sandboxes/snapshots)).

**Recommendation:** bare metal is the documented, lower-risk path. Choose Kubernetes only if its scheduling value justifies owning KVM integration, storage fencing, retries, upgrades and guest recovery; upstream supplies no such control plane.
