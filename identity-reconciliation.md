# Reconcile communication identities, not just accounts

Declare the **capability** each agent needs, then let a privileged controller provision and observe provider resources. A role or tool declaration does not itself authorize anything.

- **Zulip:** prefer a bot to a human user; generic bots can act through the API, incoming webhook bots only send, and outgoing webhook bots receive addressed messages ([bot types](https://zulip.com/help/bots-overview)). The public [create-user API](https://zulip.com/api/create-user) creates regular users (with plan/permission limits); the documented [bot creation flow](https://zulip.com/help/add-a-bot-or-integration) uses the UI. Do **not** promise automated bot creation without verifying a supported interface in the target deployment. Record the bot owner and ID after the human creation step.
- **Buzz (assuming [Block's Buzz](https://github.com/block/buzz)):** give each agent its own Nostr keypair and keep the private key outside Git. An ACP-speaking harness such as OMP can run behind Buzz's [harness-independent `buzz-acp` bridge](https://github.com/block/buzz/blob/main/crates/buzz-acp/README.md#using-any-acp-agent): this needs relay admission when enforced, access to the intended channel, an addressing mention, and an inbound author policy. Its default `owner-only` policy accepts no messages until the agent's owner is known ([Buzz ACP author gate](https://github.com/block/buzz/blob/main/crates/buzz-acp/README.md#inbound-author-gate)). The **Bot** room-role requirement previously stated here applies to the [OpenClaw plugin](https://docs.openclaw.ai/channels/buzz#bot-approval), not universally to Buzz ACP agents. See the [three-agent Kata proposal](three-agents-kata-plan.md).
- **Google Workspace:** a Directory `User` is an account, but a usable Gmail inbox also needs a mail licence and mailbox setup; creating users can incur charges ([users guide](https://developers.google.com/workspace/admin/directory/v1/guides/manage-users), [User resource](https://developers.google.com/workspace/admin/directory/reference/rest/v1/users)). An email **alias** routes to an existing mailbox; it is not an independent account ([alias semantics](https://knowledge.workspace.google.com/admin/users/add-or-delete-an-alternate-email-address-email-alias#whatEmailAlias)). Request a full user only if independent mail or sign-in is needed.
- **SCIM 2.0:** `User`, client-provided `externalId` and server-provided immutable `id` help provision identities where a provider supports SCIM; `active` is not a universal authorization policy ([RFC 7643](https://www.rfc-editor.org/rfc/rfc7643.html#section-4.1.1)). Discover provider capabilities before relying on an operation ([RFC 7644 discovery](https://www.rfc-editor.org/rfc/rfc7644.html#section-4)).

**Proposed control loop:** persist `(stable agent ID, provider, tenant, resource kind) → remote immutable ID`, owner and secret *reference* outside Git. Observe by ID; if missing, search before creating. An address match without ownership proof is a conflict, not permission to adopt. Create, save the returned ID, then re-read and verify the usable outcome; a timeout is not proof that creation failed. Patch only controller-owned fields, report drift, and keep partial successes for retry. Google warns mailbox creation is delayed; user email can change, so it should not be a persistent key ([users guide](https://developers.google.com/workspace/admin/directory/v1/guides/manage-users)). SCIM defines [uniqueness conflicts](https://www.rfc-editor.org/rfc/rfc7644.html#section-3.3) and [conditional updates](https://www.rfc-editor.org/rfc/rfc7644.html#section-3.14) when supported.

Keep provisioning credentials in the controller, not in every agent. Scope Google directory administration to that controller; domain-wide delegation is for accessing user data on behalf of users, not a prerequisite for account creation ([Google credentials](https://developers.google.com/workspace/guides/create-credentials#service-account)). Treat key rotation, suspension and deletion as separate transitions; disable first, delete only under explicit retention/ownership policy. Zulip bot keys can be regenerated, and deactivating an owner may deactivate their bots ([key rotation](https://zulip.com/api/regenerate-api-key), [deactivation](https://zulip.com/api/deactivate-user)).

**Open:** confirm that the intended service is Block's Buzz; Gmail send-as, channel memberships, licences and message retention for other services still need provider-specific policy. Related: [repository-scoped group](agent-manifest.md) · [sleeping execution](sleeping-agents.md).
